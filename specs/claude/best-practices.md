## 0. 決定論的 vs 非決定論的な指示（2026-11 改訂の中核概念）

全ての指示は2種類に分かれる:

1. **非決定論的**（Claude = モデルが判断）: プロンプト、`CLAUDE.md`、スキル。ほぼ従うが**保証はない**
2. **決定論的**（Claude Code = ハーネスが強制）: hook、deny ルール、managed settings。モデルの判断に関係なく毎回適用

| 観点 | 非決定論的（Claudeが判断） | 決定論的（Claude Codeが強制） |
|:--|:--|:--|
| 何をするか | プロンプト、`CLAUDE.md`、Claudeが自発的に使うスキル | Hooks、`disable-model-invocation` なスキル |
| 何に触れるか | auto mode の分類器 | deny ルール、strict モードのサンドボックス、managed settings |
| いつ完了か | エビデンス要求、`/goal`、`/code-review` | テスト、typecheck、`Stop` hook、CI |
| いくら使うか | effort レベル、Claude自身のペース | `-p` の `--max-turns` / `--max-budget-usd`、支出上限 |
| 最終決定権 | Claudeの作業サマリ | ブランチ保護、マージを承認する人間 |

**基本は Claude に判断させる**（ガイドラインにはほぼ例外があり、現行モデルは目の前のコードを読んで適否を判断できる）。決定論的手段は「例外ゼロで必ず/絶対」の事項だけに使う。CLAUDE.md の行に強調を足し続けているなら hook に移すサイン。逆に、単なる好みの hook は削除して Claude に任せる。

セッションが期待通りに行かないときの切り分け:
- 想定と違うものを作った / 毎回同じ事実を再発見している → リポジトリから読めない情報が不足（§1, §5.3）
- 「完了」と言ったが完了していない → 自己検証手段がない（§5.1）
- 絶対禁止の操作をした / 必須ステップを飛ばした → プロンプトでは保証不可、hook/deny へ（§4）
- 正しいが時間・トークン・承認プロンプトが掛かりすぎ → `/usage` で原因を見てデフォルト変更（§8）

## 1. CLAUDE.md 作成のベストプラクティス

### 1.1 `/init` で始める

```bash
claude
> /init
```

コードベースを分析し、ビルドシステム・テストフレームワーク・コードパターンを検出して CLAUDE.md の雛形を生成する。既存 CLAUDE.md がある場合は改善提案を行う。

`CLAUDE_CODE_NEW_INIT=true` で対話式フロー（CLAUDE.md + Skills + Hooks のセットアップ）を有効化。

生成後の手入れは「行を削る」作業が中心。支援コマンド（2026-11 ページ改訂で明記）:
- `/doctor` — コードから分かる内容の削除候補を提案
- `/doctor prompt-audit` — 旧モデル向けに書かれた指示、存在しないファイルを指す指示、矛盾する指示を検出
- `/context all` — セッション内で CLAUDE.md が読み込まれたことを確認（2026-11-05 巡回でコマンド表記を更新）

### 1.1b 書く前の2つのテスト

書き足す前に自問する:
1. コードを読めば見つけられるか？
2. 実際に見に行くか？

**両方 Yes なら書かない**。書くべきは「リポジトリに存在しない情報」（会議での決定、1人の頭の中にあるデプロイ手順、統合テストに必要な環境変数）と、「リポジトリにはあるが毎セッション数分の掘り起こしが要る情報」のみ。

### 1.2 含めるべきもの・除外すべきもの

| 含めるべき | 除外すべき |
|:--|:--|
| Claude が推測できない Bash コマンド | コードを読めば分かること |
| デフォルトと異なるコードスタイル規則 | Claude が既知の標準的な言語慣例 |
| テスト指示と推奨テストランナー | 詳細な API ドキュメント（リンクで代替） |
| リポジトリ慣例（ブランチ命名、PR規約） | 頻繁に変更される情報 |
| プロジェクト固有のアーキテクチャ決定 | 長い説明やチュートリアル |
| 開発環境の癖（必要な環境変数） | ファイルごとのコードベース説明 |
| 一般的な落とし穴や非自明な動作 | 「クリーンなコードを書く」等の自明な実践 |

### 1.3 サイズとフォーマット

- **200行以下**を目標（1ファイルあたり）
- Markdown の見出しと箇条書きで構造化
- 検証可能な具体的指示を書く
  - 良い例: 「2スペースインデント」「`npm test` をコミット前に実行」
  - 悪い例: 「コードを適切にフォーマット」「変更をテスト」
- 矛盾する指示がないか定期的に見直す

### 1.4 強調と遵守率（旧ガイダンスの反転）

**「IMPORTANT」「YOU MUST」等の強調は追加しない。** 現行モデルは平易に書かれた1行を守る。強調を重ねてもむしろルールを**過剰適用**する副作用の方が大きい（2026-10 公式ページ全面改訂で明文化。従来の「強調で遵守率向上」ガイダンスの反転）。

- 強調しても守られない行は、ファイルが長すぎて埋もれているサイン → ファイルを短くする
- 例外を許さないルールは、強調ではなく **hook または deny ルール**に移す（§4参照）

### 1.5 配置戦略

| 用途 | 配置場所 |
|:--|:--|
| 全セッション共通の個人設定 | `~/.claude/CLAUDE.md` |
| チーム共有のプロジェクト規約 | `./CLAUDE.md`（git にコミット） |
| モノレポのサブプロジェクト | `root/CLAUDE.md` + `root/foo/CLAUDE.md`（自動マージ） |
| 特定ファイルタイプ向け指示 | `.claude/rules/` にパススコープルール |
| 個人的なプロジェクトオーバーライド | `@~/.claude/my-project-instructions.md` でインポート |
| 個人の好み（リポジトリに入れない） | `CLAUDE.local.md`（`.gitignore` に追加） |

### 1.6 CLAUDE.md をコードとして扱う

- git にコミットしてチームで共同改善
- 問題発生時にレビュー・剪定する
- Claude の行動変化を観察して効果を検証
- 時間とともに価値が蓄積される

### 1.7 肥大化の対処

CLAUDE.md が長すぎると指示が無視される。対策:
- `@path/to/import` でファイル分割
- `.claude/rules/` でトピック別ファイルに分離
- `paths` フロントマターでパススコープルールを活用
- タスク固有の指示は Skills に移動（オンデマンド読み込み）

## 2. コンテキスト管理

**位置づけが変わった（2026-10 改訂）**: 現行モデルの多くは 1M トークンウィンドウを持ち、コンパクションも自動で走るため、コンテキスト枯渇は稀。「コンテキストウィンドウが最重要制約、積極的に管理せよ」は過去のアドバイスになった。ただし **`/clear` によるタスク間リセットは引き続き有効**（焦点の定まったコンテキストは回答品質を上げ、コストも下げる）。

### 2.1 基本原則

- **`/clear` を頻繁に使用**: 無関係なタスク間でコンテキストをリセット
- **`/compact` の活用**: カスタム指示付きでコンパクション可能（例: `/compact API変更に集中`）
- **`/btw` でサイドクエスチョン**: コンテキストに残らない一時的な質問
- **`/context` でコンテキスト使用量を可視化**: 最適化提案も表示

### 2.2 サブエージェントの使いどころ（コンテキスト保全目的は廃止）

**「コンテキスト保護のためにサブエージェントを使う」は廃止された**（コンテキスト枯渇自体が稀になったため）。サブエージェントが依然有効なのは:

- 独立した作業の**並列実行**（全体の完了が早まる）
- テスト全出力・広範な検索など**ノイジーな長い出力をメイン会話に持ち込まない**
- コードの作成過程を見ていない**独立レビュアー**
- メインセッションより**少ないツール**での実行（読めるが編集できないレビュアー等）

いずれもトークンコストは追加で掛かる。同じタスクを委譲しても**答えが良くなるわけではない**（フレッシュなレビュアーが効くのは「推論過程を見ていない」からで、委譲とは別の話）。

### 2.3 コンパクション戦略

- 自動コンパクションはコンテキスト限界に近づくと発動
- `/compact Focus on the API changes` のようにフォーカス指示が可能
- `Esc + Esc` または `/rewind` で部分的な要約（選択メッセージ以降を要約）
- CLAUDE.md に「コンパクション時に変更ファイル一覧とテストコマンドを保持」等の指示を記載可能

### 2.3b コストとキャッシュ（2026-11 追記）

枯渇しなくても「不要なコンテキストに払う」問題は残る。毎リクエストが会話全体を送るため、無関係な3タスクを抱えたセッションは4つ目の全ターンでそれを再読する。

- **`/usage` が最初の確認先**: Pro/Max/Ultra/Team/Enterprise ではスキル・サブエージェント・プラグイン・MCPサーバー別に使用量を分解表示。長いコンテキストや頻繁なキャッシュミスが使用量の10%を超えるとフラグ
- **`/clear <名前>`**（例: `/clear oauth-migration`）で離れるセッションに名前を付けて後で戻れる。`/rename <名前>` + `claude --resume <名前>` も同様
- **プロンプトキャッシュ寿命**: サブスクリプションは約1時間、APIキー/クラウドプロバイダ/usage credits は5分。サブエージェントは既定5分
- 1時間キャッシュでは、約200Kトークン超のアイドルセッションはキャッシュ失効直前に自動コンパクトされる（昼食後はサマリから再開）。履歴が不要なら新セッションの方が安い
- バックグラウンド作業（`/loop`、goal の毎ターンチェック、サブエージェント）は入力していない間もリクエストを送り続ける

### 2.4 アンチパターン: キッチンシンクセッション

1つのタスクから無関係な質問に移り、また元に戻る。コンテキストが不要情報で汚染される。

**対策**: `/clear` でタスク間をリセット。

### 2.5 アンチパターン: 繰り返し修正

2回以上修正しても改善しない場合、コンテキストが失敗アプローチで汚染されている。

**対策**: `/clear` してより良い初期プロンプトを書き直す。

### 2.6 セッション操縦の基本操作（2026-11 追記）

最初の1分を見て、逸れた瞬間に `Esc`。修正2回失敗したら3回目ではなく `/clear` + 改善プロンプト。

- `Esc` — 実行中のアクションを止めて途中までの成果は保持
- `/rewind`（または空プロンプトで `Esc` 2回）— コード・会話・両方を過去のプロンプト時点に巻き戻し。大胆なアプローチを先に試してダメなら戻す、が低リスクに。同メニューで会話の部分要約も可能
- **注意**: チェックポイントはメイン会話でClaude自身のファイルツールが編集したファイルのみ対象。**Bashコマンドだけが触ったファイルは復元されない**。gitの代替ではなく併用
- `/btw` — 履歴に残さないサイドクエスチョン

## 3. Skills 設計

### 3.1 リファレンスコンテンツ vs タスクコンテンツ

- **リファレンス**: コーディング規約・パターン・ドメイン知識。インラインで実行
- **タスク**: デプロイ・コミット等のステップバイステップ指示。`disable-model-invocation: true` 推奨

### 3.2 設計ガイドライン

- `SKILL.md` は500行以下。詳細は別ファイルに分離
- `description` は Claude が自動適用を判断できる具体的なキーワードを含める
- 副作用のあるワークフロー（deploy, commit）は `disable-model-invocation: true`
- バックグラウンド知識は `user-invocable: false`
- `context: fork` で隔離が必要なタスクをサブエージェントで実行

### 3.3 動的コンテキスト注入の活用

`` !`command` `` で実行時にデータを注入:

```yaml
---
name: pr-summary
context: fork
agent: Explore
allowed-tools: Bash(gh *)
---

## PRコンテキスト
- PR diff: !`gh pr diff`
- コメント: !`gh pr view --comments`
```

### 3.4 スキルのコンテキストバジェット

スキル一覧（名前＋説明）のバジェットは**コンテキストウィンドウの 1%**（`skillListingBudgetFraction`、既定 `0.01`）。溢れると呼び出し頻度の低いスキルから説明が落とされる。1スキルあたり `description` + `when_to_use` 合算 **1,536 文字**上限（`skillListingMaxDescChars`）。`SLASH_COMMAND_TOOL_CHAR_BUDGET` で固定文字数指定も可能。詳細は skills-and-commands.md §7。

## 4. Hooks 活用

### 4.1 Hooks が適する場面

- **例外なく毎回実行すべきアクション**: ファイル編集後のリント、コミット前のテスト
- **セキュリティポリシーの強制**: 破壊的コマンドのブロック、機密ファイルへの書き込み防止
- **環境のセットアップ**: セッション開始時の環境変数設定

hook は**例外ゼロのルール専用**。「named export を推奨」のような例外だらけの好みは CLAUDE.md に残す。強制セットは小さく保つ（40個もあれば大半は Claude に任せられる好み）。

### 4.1b ハンドラ種別と決定論性（2026-11 追記）

hook のハンドラは シェルコマンド / HTTP POST / MCPツール呼び出し / `prompt`・`agent`（モデルに判断させる）の4種。**`prompt`/`agent` hook は別モデルの判断なので決定論的ではない**。本当の強制には `command` か `http` を使い、hook 自体のクラッシュ/タイムアウト時にもアクションを止めたいなら `onFailure: "block"` を付ける（例: secret スキャナが落ちている間にコミットを素通りさせない）。

### 4.1c Stop hook で完了チェックを強制

`Stop` hook はターン終了のたびに実行され、**exit code 2 で終了を阻止**。stderr の出力が「まだ終われない理由」として Claude に返るため、コンパイラ出力は stderr にリダイレクトする:

```json
{
  "hooks": {
    "Stop": [{
      "hooks": [{ "type": "command", "command": "pnpm tsc --noEmit 1>&2 || exit 2" }]
    }]
  }
}
```

ツール呼び出しなしで**8回連続ブロック**されると Claude Code が次のブロックを無効化してターンを終了する。上限は `CLAUDE_CODE_STOP_HOOK_BLOCK_CAP` で変更可能。

### 4.2 Claude に Hooks を書かせる

```
ファイル編集ごとに eslint を実行するフックを書いて
```

```
migrations フォルダへの書き込みをブロックするフックを書いて
```

### 4.3 主要パターン

#### ファイル編集後の自動フォーマット

```json
{
  "hooks": {
    "PostToolUse": [{
      "matcher": "Edit|Write",
      "hooks": [{ "type": "command", "command": "npx prettier --write" }]
    }]
  }
}
```

#### 破壊的コマンドのブロック

```json
{
  "hooks": {
    "PreToolUse": [{
      "matcher": "Bash",
      "hooks": [{ "type": "command", "command": ".claude/hooks/block-destructive.sh" }]
    }]
  }
}
```

#### セッション開始時のコンテキスト注入

```json
{
  "hooks": {
    "SessionStart": [{
      "hooks": [{ "type": "command", "command": ".claude/hooks/session-context.sh" }]
    }]
  }
}
```

### 4.4 `/hooks` で確認

設定済みフックの読み取り専用ブラウザ。イベント・matcher・ハンドラ設定・ソース元を表示。

## 5. 効果的なプロンプティング

### 5.1 検証手段を提供する

Claude に自己検証の手段を与えることが最大のレバレッジ:

- テストケースを明示: 「`user@example.com` は true、`invalid` は false」
- テスト実行を指示: 「実装後にテストを実行して失敗を修正」
- スクリーンショット比較: 「このデザインを実装してスクリーンショットで比較」

チェックの厳しさは4段階から選べる（2026-11 改訂で段階が明文化）:

| 段階 | 手段 | 性質 |
|:--|:--|:--|
| プロンプト内 | 「テストを実行し、通るまで続けて」 | Claude が自分で満足を判断。設定不要で今すぐ使える |
| ゴール | `/goal all tests in tests/auth pass and lint is clean` | 別モデルが毎ターン後に会話を条件照合し、満たすまで戻す。長時間バックグラウンド実行向け |
| Stop hook | exit 2 でターン終了を阻止（§4.1c） | **ハーネスが強制**。typecheck が通るまで終われない |
| 独立レビュー | `/code-review`（会話を見ていないサブエージェントで diff レビュー） | コードを生んだ推論に引きずられない |

どの段階でも**エビデンスを要求する**: 実行したコマンドと出力、またはスクリーンショット。「全テストパス」だけでは情報がほぼなく、出力を読む方が自分で再実行するより速い。完了後に `/verify` でアプリを実際にビルド・実行して確認させるのも有効（テストや typecheck が見落とす種類の問題を捕まえる）。

仕様に対するレビューを頼むときは `skip style` を忘れない（「問題を探せ」と言われたレビュアーは必ず何かを見つける。全指摘を直すと不要な抽象レイヤーと起こり得ないケースのテストが増える）。

### 5.2 探索 → 計画 → 実装

1. **探索**: プランモードでコードベースを読む
2. **計画**: 実装計画を作成させる（`Ctrl+G` でエディタで編集可能）
3. **実装**: ノーマルモードで実装
4. **コミット**: コミット・PR作成

小さな修正（タイポ、ログ追加、リネーム）は計画をスキップして直接実行。

**注**: 2026-11 のページ再改訂で「探索→計画→実装」の4フェーズワークフロー節は公式ベストプラクティスから削除された（プランモード自体は健在。ページの重心が「具体的なプロンプト＋検証手段」に移った）。手順自体は依然有効なパターンとして残す。

### 5.3 具体的なコンテキストを提供

- ファイルを `@` で参照
- 画像をペースト/ドラッグ&ドロップ
- URL を提供
- `cat error.log | claude` でデータをパイプ
- 既存パターンを指し示す: 「HotDogWidget.php をパターンとして参照」

### 5.3b `be ambitious`（2026-11 追記）

今も効くフレーズは **`be ambitious`**。Claude はリクエストを控えめに読み、要求を満たす最小のものを作る傾向がある（どこまで望んでいるかが見えないため）。エッジケース対応や自然な続きまで含めたフルバージョンが欲しければ明示する:

```text
build the settings page from the mockup. be ambitious: empty and error states, the save flow wired up, keyboard navigation, not just the layout
```

これは「どれだけ考えるか」ではなく**自分にしか分からないスコープ**を伝えるもの（思考量は effort が制御。§8.1）。

### 5.4 Claude にインタビューさせる

```
[簡潔な説明]を作りたい。AskUserQuestion ツールを使って詳しくインタビューして。
技術実装、UI/UX、エッジケース、懸念点、トレードオフについて聞いて。
全てカバーしたら SPEC.md に完全な仕様を書いて。
```

仕様完成後、新しいセッションで実装を開始（クリーンなコンテキスト）。SPEC.md は後の独立レビューの照合先にもなる（§5.1 の `skip style` パターン）。

### 5.5 外部システムへの接続（2026-11 追記）

- 外部システムに CLI があるなら**それが最も簡単な接続手段**（`gh` がインストール・サインイン済みなら説明不要で PR 作成・レビューコメント読み取り可能。未知の CLI は `--help` を指させれば十分）
- CLI がないものは MCP（`claude mcp add --transport http ...`）。ただし**接続済みサーバーは使っていなくてもツール名と指示をコンテキストに足す**ため、`/mcp` で不要なものは無効化する
- 型付き言語ならコード intelligence プラグインで定義ジャンプ（複数ファイル読み漁りの代替）

## 6. 組織・チーム向け運用

### 6.1 Managed CLAUDE.md

組織全体の指示を IT/DevOps が配布:

- macOS: `/Library/Application Support/ClaudeCode/CLAUDE.md`
- Linux/WSL: `/etc/claude-code/CLAUDE.md`
- Windows: `C:\Program Files\ClaudeCode\CLAUDE.md`

MDM / Group Policy / Ansible 等で配布。除外不可。

### 6.2 Managed Settings vs Managed CLAUDE.md

| 用途 | 設定場所 |
|:--|:--|
| ツール・コマンド・ファイルパスのブロック | Managed settings: `permissions.deny` |
| サンドボックス隔離の強制 | Managed settings: `sandbox.enabled` |
| 環境変数・APIプロバイダ | Managed settings: `env` |
| 認証方式・組織ロック | Managed settings: `forceLoginMethod`, `forceLoginOrgUUID` |
| コードスタイル・品質ガイドライン | Managed CLAUDE.md |
| データハンドリング・コンプライアンス | Managed CLAUDE.md |
| Claude の行動指示 | Managed CLAUDE.md |

### 6.3 プロジェクト標準化

- `.claude/settings.json` をバージョン管理にコミット
  - コミットした deny ルールは即適用。`allow` ルールは各メンバーがフォルダの trust ダイアログを承認してから、hooks も workspace trust 後に発動（2026-11 追記）
- `.claude/skills/` をチームで共有
- `.claude/agents/` をプロジェクト固有のサブエージェントとして共有
- `.mcp.json` でプロジェクト共通の MCP サーバーを定義

### 6.4 権限管理

- **Auto mode が既定の開始モード**: **v2.1.283 以降、プランを問わず**対話ターミナル / VS Code セッションの組み込み開始権限モードは auto mode（分類器がほとんどのアクションを代行レビューし、スコープ逸脱・未知のインフラ・敵対的コンテンツ由来の操作のみブロック）。それ以前は Pro / Max / Team プランのみが auto mode 開始だった（2026-10 ドキュメント改訂で確認）
- **権限許可リスト**: 安全と分かっているツールを許可（`npm run lint`, `git commit`）
- **サンドボックス**: OS レベルの隔離で安全な自由実行を実現
- **`--dangerously-skip-permissions`**: インターネットアクセスのないサンドボックス内でのみ使用

#### deny ルールの効く範囲と限界（2026-11 追記）

`deny` ルールは auto / `bypassPermissions` を含む**全権限モードで有効**。だからこそ `.env` 禁止は deny に置く。ただしルールはツール呼び出しにマッチするのであって意図にではない:

- `Read(./.env)` の deny は `cat .env` も**捕まえる**（一般的なファイル読み取りコマンドを認識）
- ファイルを開くスクリプト経由は**捕まえない**
- `WebFetch` の domain deny は同ドメインへの `curl` に**効かない**（サンドボックスONなら効く）

OSレベルで塞ぐにはサンドボックス（`/sandbox`）を併用（`Read` deny と `WebFetch(domain:...)` を引き継ぐ）。既定ではブロックされたコマンドのサンドボックス外リトライを Claude が要求できるが、**strict sandbox mode**（`/sandbox` の Overrides タブ）でリトライ自体を無効化できる。

auto mode は分類器モデルの判断であり、hard rule ではない（間違い得るし、組織が無効化もできる）。「絶対禁止」は deny ルールか hook に置く。

#### auto mode のチューニング（2026-11 追記）

- ブロック時は通知が来て `/permissions` の **Recently blocked** に表示、承認してリトライさせられる。**3回連続**（または計20回）ブロックで auto mode は一時停止して確認モードに戻る
- 会話中の「レビューまで push しないで」も分類器がブロックシグナルとして扱うが、コンパクションで消え得るため重要事項は deny ルールへ
- 定常的に止められるルーチン操作は `autoMode.allow` / `autoMode.environment` に平文英語で記述。`/auto-mode-setup` が `environment` の下書きを生成
- **`"$defaults"` を各リストに必ず残す**（無いと組み込みルールを置き換えてしまう。`soft_deny` では force push・本番デプロイの組み込みブロックが消える）
- **`autoMode` ブロックは `~/.claude/settings.json` のみ有効**（プロジェクト settings の `autoMode` は分類器が無視）
- Manual モードでプロンプトが多すぎる場合は `/fewer-permission-prompts` が最近のトランスクリプトから読み取り専用の Bash/MCP 呼び出しを抽出して許可リスト化

### 6.5 並列作業によるスケーリング

- **デスクトップアプリ**: 複数ローカルセッションの視覚的管理
- **Web**: Anthropic クラウドインフラで隔離VM実行
- **エージェントチーム**: 共有タスク・メッセージング・チームリードによる自動調整
- **Writer/Reviewer パターン**: 1つのセッションで実装、別のセッションでレビュー

### 6.6 ファンアウトパターン

大規模マイグレーションや分析を並列化。`/batch <instruction>` なら Claude が変更を 5〜30 の作業単位に分割して**計画を提示し、承認すると**各単位が自分の worktree で作業して **PR を開くか結果を報告**する（2026-11-05 巡回で計画承認→PR/報告のフローを反映）。自前スクリプトでファンアウトする場合:

```bash
for file in $(cat files.txt); do
  claude -p "Migrate $file from React to Vue. Return OK or FAIL." \
    --allowedTools "Edit,Bash(git commit *)" \
    --permission-mode dontAsk
done
```

`--allowedTools` が必要ツールを事前承認し、`--permission-mode dontAsk` が承認が必要なその他の操作を拒否する（無人実行時に重要）。最初の 2〜3 ファイルで失敗パターンを見てプロンプトを調整してから全件に回す。

### 6.7 非対話モード

CI/CD パイプラインやスクリプトでの使用:

```bash
# 単発クエリ
claude -p "このプロジェクトが何をするか説明して"

# 構造化出力
claude -p "全APIエンドポイントを一覧" --output-format json

# ストリーミング
claude -p "このログファイルを分析" --output-format stream-json
```

スクリプトでの推奨フラグ（2026-11 追記）:
- **`--bare`** — hooks / skills / plugins / MCP / CLAUDE.md（リポジトリ・マシン両方）をスキップし、どこで実行しても同じ挙動に。claude.ai ログインには触れず、認証は `ANTHROPIC_API_KEY`・`--settings` の `apiKeyHelper`・クラウドプロバイダ資格情報から
- `--append-system-prompt` / `--mcp-config` / `--settings` — 実行に必要なものだけを明示的に渡す。ただし **`--settings` で渡した hooks は `--bare` 下では実行されない**（hooks が必要な実行に `--bare` は使わない。2026-11-06 best-practices 改訂で明文化）
- `--allowedTools` + `--permission-mode dontAsk` — 事前承認＋それ以外は拒否
- `--max-turns` / `--max-budget-usd` — 暴走の上限
- auto mode も `-p` で使用可（`--permission-mode auto`）。非対話実行では分類器ブロックはその1アクションの拒否のみで続行し、連続ブロックでも停止しない

### 6.8 無人実行前の5つの質問（2026-11 追記）

タスクを放置実行する前にそのタスクについて確認する:

1. **「完了」が分かるか？** goal 条件、spec ファイル、green にすべき失敗テスト
2. **自己検証できるか？** テストスイート、`Stop` hook、レビューステップ
3. **何に触れてよいか？** 権限ルール、`dontAsk`、サンドボックス、worktree、push 可能な1ブランチ
4. **何が止めるか？** `--max-turns`、`--max-budget-usd`、支出上限
5. **結果はどこへ行き、誰が承認するか？** PR / コメント / サマリ → 取り返しのつかない操作は人間が承認

起動手段: セッション内の `/loop <間隔> <プロンプト>`（同一セッションのターンとして繰り返す。長い会話では使わない）、ラップトップを閉じても動かすなら `/schedule` のクラウドスケジュールタスク（claude.ai ログイン必須）。タイマー以外に **GitHub イベントトリガー**（Claude に頼めば追加できる）と **API トリガー**（claude.ai/code/routines で設定）も使える（2026-11-05 巡回で反映）。クラウドタスクを放置する前に **main をタスクが迂回できない GitHub ブランチルールで保護**し、最初の数回は実行を見守る。

### 6.9 worktree 並列実行（2026-11 追記）

- `claude -w feature-auth` で新 worktree にセッションを開始。デスクトップアプリで複数並走、クラウドセッションはクラウドで実行
- worktree は新規チェックアウトなので gitignore されたファイル（`.env` 等）が無い → リポジトリルートの **`.worktreeinclude`**（`.gitignore` と同じ構文）に列挙すると作成時にコピーされる。コピーでありリンクではないため小さいファイルに限る。大きいディレクトリは `worktree.symlinkDirectories` 設定か、CLAUDE.md にインストールコマンドを書く
- 後片付けはほぼ自動: 無名セッションは終了時に空なら削除、サブエージェント worktree は変更なしなら消える、残骸は `cleanupPeriodDays` 超で掃除。**`claude -p --worktree` だけは手動掃除**（`git worktree remove`、ロック時は先に `unlock`）
- `claude agents`（research preview）でバックグラウンド実行中のもの一覧を1画面で確認

## 7. よくある失敗パターンと対策

| パターン | 問題 | 対策 |
|:--|:--|:--|
| キッチンシンクセッション | 無関係なタスクの混在 | `/clear` でタスク間をリセット |
| 繰り返し修正 | 失敗アプローチでコンテキスト汚染 | 2回失敗後、`/clear` して改善プロンプト |
| 肥大化 CLAUDE.md | 重要な指示がノイズに埋もれる | 剪定。正しく動作する指示は削除またはフックに変換 |
| 信頼→検証ギャップ | エッジケース未対応の実装 | テスト・スクリプト・スクリーンショットで検証 |
| 無限探索 | スコープなしの調査でコンテキスト消費 | 調査を狭くスコープ、またはサブエージェント使用 |

## 8. デフォルト変更の指針（Change a default）

デフォルト（auto mode、Opus 5.5 / medium effort、自動委譲、自動コンパクション）は基本的にそのままでよい。タスクが時間・トークン・中断のコストに見合わなくなったときだけ `/usage` で原因を見て変更する。

### 8.1 effort が思考量の主制御

**effort レベルが「どれだけ考えるか」の主制御**で、従来プロンプト文言でやっていたことの大半を置き換える。Opus 5.5 / Sonnet 5.5 / Haiku 5.5 の既定は `medium`。セッション内で `/effort` で変更:

| 設定 | 使いどころ |
|:--|:--|
| `high` / `xhigh` | 見落としやすいケースに正否が掛かる作業（他人のコードのバグ、flaky テスト、旧スキーマの全読み取り箇所を探すスキーマ変更） |
| `low` | 高速に往復しながら毎回レビューする作業（ブレスト、最初のスケッチ、数ファイルのリネーム） |
| `max` | 無人で解かせる難問（脆弱性ハント等）のみ。通常タスクでは考えすぎになり、`high` と変わらない答えに余計に払うことになる |
| `ultrathink`（プロンプト内） | **次の1メッセージだけ**深い推論が欲しいとき。effort 設定を変えずにその1ターンの推論を引き上げる唯一のキーワード |

`think hard` / `think harder` / `think step by step` / `be thorough` 等は**キーワードではなく普通のプロンプトテキスト**。effort 設定の範囲内で多少の後押しにはなるが、設定を超えて引き上げることはない。

モデル選択: 既定の Opus 5.5 がほとんどのコーディングに対応し、ルーチン作業には Sonnet が安価。**Claude Fable 5.1 は `/model fable` で明示選択したときのみ**使われる。Haiku は単純作業のサブエージェント向き（2026-11 追記）。

### 8.2 サブエージェントのコストを知る

Claude は自発的に委譲する。知っておくべきデフォルト:

- 広いコードベース検索は組み込み **Explore エージェント**に行く
- サイドタスクは **fork**（既定で有効）される
- Claude が起動するサブエージェントは**既定でバックグラウンド実行**（メイン会話は止まらない）

コストは主にトークン（各サブエージェントが独自にリクエストを送り、同じ使用量枠を消費）。フレッシュなサブエージェントはコンテキスト収集からやり直すため、**その場でやるより遅くなることもある**。節約策: 単純作業は定義に `model: haiku`、返答は短い要約を要求、`/usage` でタイプ別の使用割合を確認、レビュアー定義には `tools: Read, Grep, Glob` のみ付与。

## 9. 廃止された従来アドバイス（What you can stop doing）

公式ページに「やめてよいこと」の表が追加された（2026-10 改訂）。いずれも当時は正しかったが、モデルの進歩で不要になったワークアラウンド:

| 旧アドバイス | 廃止理由 |
|:--|:--|
| コンテキストウィンドウが最大の制約、積極管理せよ | 1M ウィンドウ＋自動コンパクションで枯渇は稀。**`/clear` のタスク間リセットだけは引き続き有効** |
| 指示に IMPORTANT / 大文字強調を足す | 現行モデルは平易な1行を守る。強調はルールの過剰適用を招く。曲げられないルールは hook / deny ルールへ。埋もれるならファイルを短く |
| コンテキスト保護のためサブエージェントを使う | 枯渇が問題でなくなった。並列作業・ノイズ隔離・独立レビューには依然有効（ただしトークン追加コスト） |
| より良い答えのためにサブエージェントへ委譲 | 同じタスクを渡しても答えは良くならない。効くのは「推論を見ていないフレッシュなレビュアー」であり、委譲とは別物 |
| `think hard` / `think harder` / `be thorough` | effort が制御手段。これらは effort 設定内で後押しする普通のテキスト。**`ultrathink` のみ**が単一ターンの推論を引き上げるキーワードとして残存 |
| 「続けろ」「怠けるな」と指示する | 現行モデルは合意済みタスクを言われなくても継続する。この種の行はむしろ過剰作業を招く。止まったら `continue`、無人実行は `/goal` か Stop hook で強制 |
| CLAUDE.md にアーキテクチャ・ファイル構成を書く | Claude は自分でリポジトリを読む。リポジトリに無い情報だけ書く |
