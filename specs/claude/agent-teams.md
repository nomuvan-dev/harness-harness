# Claude Code Agent Teams 仕様

最終更新: 2026-08-30（巡回更新）

複数のClaude Codeインスタンスを協調動作させる実験的機能。サブエージェント（結果を返すだけ）と異なり、チームメイトは独立したコンテキストウィンドウを持ち、相互にメッセージングできる。

公式ドキュメント: https://code.claude.com/docs/en/agent-teams

---

## 1. 有効化

```json
// .claude/settings.json
{
  "env": {
    "CLAUDE_CODE_EXPERIMENTAL_AGENT_TEAMS": "1"
  },
  "teammateMode": "in-process"
}
```

または環境変数: `export CLAUDE_CODE_EXPERIMENTAL_AGENT_TEAMS=1`

## 2. アーキテクチャ

| コンポーネント | 役割 |
|---------------|------|
| リード | チームを作成・統括するメインセッション |
| チームメイト | 独立したClaude Codeインスタンス。各自1Mトークンのコンテキストウィンドウ |
| 共有タスクリスト | `~/.claude/tasks/{team-name}/` に保存。依存関係サポート |
| メールボックス | ピアツーピアメッセージング |

## 3. API

### チームの作成（v2.1.178で刷新）

**`TeamCreate` / `TeamDelete` ツールは v2.1.178 で削除された。** `CLAUDE_CODE_EXPERIMENTAL_AGENT_TEAMS=1` が有効なら全セッションが暗黙の1チームを持ち、セットアップ手順なしで `Agent` ツールの `name` パラメータでチームメイトを直接スポーンする。`Agent` ツールの `team_name` パラメータは受理されるが無視される。

v2.1.178未満の旧バージョンでは従来どおり `TeamCreate`（リードのみ呼び出し可）→ `TeamDelete`（全チームメイトシャットダウン後）のフロー。

### SendMessage
- メッセージ種別:
  - `message`: 特定チームメイトへの直接メッセージ
  - `broadcast`: 全チームメイトへ一斉送信
  - `shutdown_request`: グレースフルシャットダウン要求
  - `shutdown_response`: シャットダウン承認/拒否
  - `plan_approval_response`: 計画のクオリティゲート
- **クロスセッション中継のセキュリティ強化（v2.1.166）**: 他の Claude セッションから `SendMessage` 経由で中継されたメッセージはユーザー権限を持たないものとして扱われる。受信側は中継経由の権限リクエストを拒否し、auto mode は該当をブロックする
- **名前再利用の誤配送検出（v2.1.199）**: 再スポーンされたエージェントが以前のエージェント名を再利用した場合、ミスマッチを検出して呼び出し元に再ターゲットを要求する
- **`@` メンションでのセッション指名（v2.1.232）**: プロンプトで `@` を入力して他の Claude セッションを名前で指名すると、Claude が `SendMessage` でそのセッションに直接到達する
- **生の名前での配送（v2.1.232）**: 名前が稼働中セッション1つと完全一致する場合、ref による確認を求めず直接配送する（曖昧な場合のみ ref を要求）
- **セッション名の一意性（v2.1.232）**: 同一マシン上で既存の稼働中セッションと同名を指定して起動・リネームすると `name-word-word` 形式のバリアントが自動付与され、その旨が通知される
- **受信制御（v2.1.232）**: `/config` に「Messages from your other sessions」（accept / hold / refuse）と「Dialog expiry」の行が追加。設定キーは `crossSessionInbound` / `dialogExpiry`
- **`notify_when_idle`（v2.1.236）**: 同一マシン上の他 Claude Code セッションに対し「次にアイドルになったとき一度だけ通知して」と依頼するオプトイン・ワンショットのオプション。ポーリング不要。macOS / Linux 対応
- **過大メッセージ / バーストの事前拒否（v2.1.235 / v2.1.236）**: セッション間配送に対して大きすぎるメッセージは送信前に拒否される（v2.1.235）。また短時間の連投が受信側インボックスの受容量を超える場合、「送信済み」と報告してから破棄せず、以降のメッセージを送信前に拒否する（v2.1.236）

### セッション間メッセージ（Cross-session messaging）

専用ドキュメント: https://code.claude.com/docs/en/cross-session-messaging

Agent Teams（1セッション内の統率されたチーム）とは別に、**ユーザー自身が独立に起動した複数セッション間**でメッセージを受け渡す仕組み。Claude は `ListAgents` で到達可能な相手を探し、`SendMessage` で名前指定して送る（同じ `SendMessage` がサブエージェント・チームメイト・他セッションの3用途を兼ねる）。

**要件・可用性**（ハーネス設計時の前提確認に重要）:
- v2.1.224 以降（macOS / Linux / WSL 2）。**ネイティブ Windows は v2.1.234 以降**
- **v2.1.248 で「同一マシン内」と「マシンをまたぐ」で可用性が分離された**:
  - **同一マシン上のセッション同士**: Amazon Bedrock / Claude Platform on AWS / Google Cloud's Agent Platform / Microsoft Foundry を含む**全プロバイダで利用可能**。機能フラグ取得をオフにしていても利用可能（いずれも v2.1.248 以降が必要）。配送はマシン上のセッション単位ソケットのみで Anthropic サーバーを経由しない。止めたい場合は `crossSessionInbound: "refuse"`
  - **マシンをまたぐ相手（Claude Code on the web / 他マシン）**: Remote Control に接続したセッションからのみ探索でき、claude.ai サインインが当該セッションの有効な認証である必要がある。API キー認証や Bedrock / AWS / Agent Platform / Foundry では探索できない
  - v2.1.248 より前は、上記プロバイダや機能フラグ取得オフでは同一マシン内も含め一律で利用不可だった
- 確認手段は `/list-agents`（= `/peers`）。コマンド自体が未認識なら機能が無い

**送れるもの・送れないもの**:
- 送られるのは **Claude が書いたプレーンテキストのみ**。会話履歴・ファイル・チームの構造化プロトコルメッセージは渡らない。会話ごと移したい場合は `/resume` を使う
- 受信側での扱いは制限される: 承認の代替にならない（保留中の権限プロンプトに答えられない）、権限設定・CLAUDE.md 等の**設定変更を依頼されても行わない**、メッセージ本文中の `/compact` 等のコマンドは**実行されず単なるテキストとして届く**、必要な権限プロンプトは通常通り発火する
- 送信側の Claude は、自セッションで拒否・ブロックされた行為を他セッションに代行させないよう指示されている（権限境界はセッション単位）

**受信時の表示（v2.1.247 で変更）**: 到着メッセージは会話に**1 行のプレビュー**として出る（例 `› Message from @api-worker: Schema migration finished (ctrl+o to expand)`。送信者名 + 本文 1 行目、長ければ `…` で切られる）。全文を見るには `Ctrl+O` のトランスクリプトビューアを開くか、`--verbose` 付きセッションで起動する。**プレビューはユーザーの表示だけを短くするもので、Claude は常に全文を読む**。v2.1.247 より前は全文が会話に表示されていた。

**`/rename` の共有記録**: セッション名を変更すると他セッションが参照する共有記録も更新される。更新に失敗した場合は `/rename` の出力で「他セッションには旧名が残るかもしれない」と警告される（原因は `--debug` でログ出力）。

**受信箱ソケットのディレクトリ（v2.1.248）**: macOS / Linux では、他ユーザー所有などで受け入れられないディレクトリにはソケットを作らず、ユーザー専用の `/tmp/cc-socks-<uid>` にフォールバックする。どのディレクトリも受け入れられない場合はそのセッションは受信箱なしで動作し、通知が出て `/status` の `Peer address` 行に `unavailable` と理由が表示される（詳細は `--debug` ログ）。

**`@` メンションの扱い（ドキュメント追記）**: 新しいターンを開始するメッセージ本文に `@` 直後のパスでファイルが書かれていた場合、**受信側マシンのそのファイルが添付される**（相対パスは受信セッションのワーキングディレクトリ基準、受信側の `Read` deny ルールが適用される）。`@` で MCP リソースが書かれていた場合は受信側の MCP サーバーからそのリソースが添付される。`@` なしのパスはただのテキスト。**ターン実行中に読まれたメッセージ**はプレーンテキスト扱いで何も添付されない。

**サブエージェント発のメッセージ（v2.1.248）**: サブエージェントが書いたメッセージは送信元セッション名で届き、本文中でサブエージェントが識別される。**返信は送信元セッションのメイン会話に届き、サブエージェントには戻らない**。

**Remote Control 接続中の `/list-agents`**: ローカルセッションの詳細が一部伏せられる（ワーキングディレクトリの非表示、人に帰属できないセッション名の非表示＝`(unnamed session)` 表示、自セッション名の行は当該端末で `--name` / `/rename` により名前を打った場合のみ表示）。出力の末尾に伏せた旨の注記が出る。Claude 自身が送信先を探す際の情報は変わらない。

**外部からのメッセージ投函（ソケット直叩き）**: 投函するメッセージが確定してから接続を開くこと。**完全な 1 行を 30 秒以内に送らない接続は Claude Code 側で切断される**ため、時間のかかるコマンドの出力は先に取得してから接続する。

**配送経路**:

| 相手の所在 | 経路 |
|:--|:--|
| 同一マシン | セッション単位の Unix ドメインソケット。Anthropic サーバーを経由しない |
| 自分の別マシン | Anthropic サーバー経由 → 相手マシンの Remote Control 接続（v2.1.225 以降は会話の開始も可。それ以前は返信のみ） |
| Claude Code on the web | Anthropic サーバー経由でクラウドセッションへ直送 |

同一マシン配送はディスク上の登録ファイルとソケットに依存するため、**コンテナ内セッションとホスト側セッションは相互に到達できない**（同一コンテナ内同士は可、self-hosted runner 上を含む）。

**受信制御 `crossSessionInbound`**（`accept` / `hold` / `refuse`）が未設定のときの既定判定は、送受信セッションの権限モードを2クラス（権限プロンプトを飛ばす `bypassPermissions` 系 / それ以外の `auto`・`acceptEdits`・`dontAsk` 等）に分けて決まる:
- **受信側がプロンプトするクラス**: 原則配送。送信側が bypass クラスを名乗る場合のみ承認保留
- **受信側が bypass クラス**: 原則承認保留。送信側も bypass クラスの場合のみ配送
- 保留ダイアログが `dialogExpiry`（既定5分）を過ぎると破棄。`"never"` でセッション終了まで保持。バックグラウンドセッションは端末が未接続の間は期限を超えても開いたままになる
- 保留中に権限モードクラスが変われば再判定され、`refuse` が適用されるようになると保留分は全破棄され各送信者に拒否が通知される
- 保留は最大100件（超過分は古いものから破棄）、配送待ちキューは1セッション50件が上限

**`-p`（headless）セッション**: 通常セッション同様に受信箱ソケットを bind するため長期稼働ワーカーが受信可能。ただし bare モードでは bind せず一覧にも出ない。承認ダイアログを出せないため既定保留分は `dialogExpiry` 経過で破棄される。無人ワーカーに受信させるには `--settings` で `crossSessionInbound: "accept"` を渡す。

**無効化**（送受信は別制御）:
- 受信停止: `crossSessionInbound: "refuse"`
- 送信・一覧停止: `permissions.deny` に `SendMessage` / `ListAgents`（いずれも specifier なしの素のツール名）を追加。**`SendMessage` を deny するとサブエージェント・チームメイトへのメッセージも同時に失われる**点に注意
- 組織全体で止める場合は managed settings で両者を併用する

**ループ対策**: 送信者単位のレート制限、短時間内の同一メッセージ重複破棄、配送待ち上限50件により、2セッション間のメッセージループは自然停止する。

### サブエージェント fork（v2.1.232 でデフォルト有効）

`Agent` ツールの `subagent_type: "fork"` は会話全体とプロンプトキャッシュを継承したサブエージェントを生成する。v2.1.232 でデフォルト有効化され、あわせて対話セッションにおけるチームメイト以外のエージェントスポーンは既定でバックグラウンド実行となった。fork はモデル指定を無視し、常に親のモデルを継承する。

## 4. 表示モード

| モード | 設定値 | 説明 |
|--------|--------|------|
| in-process | `"in-process"` | メインターミナル内。Shift+Downでチームメイト間を切り替え |
| tmux分割 | `"tmux"` | 各チームメイトが独立ペイン。全出力を同時表示 |
| iTerm2分割 | `"iterm2"` | iTerm2ペイン利用（v2.1.186）。`it2` CLIが必要（見つからない場合auto modeで警告） |
| 自動 | `"auto"` | tmux内ならsplit、それ以外はin-process |

- tmux/ペインバックエンドでスポーンされたチームメイトはリードの `--effort` レベルを継承する（v2.1.186）

## 5. 計画承認（Plan Approval）

複雑・リスクのあるタスクでは、チームメイトに実装前の計画を立てさせられる。**ドキュメント改訂（2026-08 時点）で発動条件と承認の扱いが変わった**:

- 発動条件は「プロンプトで計画承認を要求する」ではなく、**リードが plan モードのときに spawn されたチームメイト**が読み取り専用の plan モードで動く。先にリードを plan モードに切り替えてからチームメイトを依頼する

```
（リードを plan モードにしたうえで）
Spawn an architect teammate to refactor the authentication module.
```

- 計画完了後、チームメイトはリードに承認リクエストを送信する
- **リードのセッションはリクエスト到着と同時に自動承認する**（リードが計画をレビューして可否を判断するわけではない）。「テストカバレッジを含む計画のみ承認」のようなプロンプトによる判断基準の制御は現行仕様では効かない
- 承認後もチームメイトの編集・コマンドは通常どおり権限プロンプトを通る

## 6. Hooksとの連携（品質ゲート）

Agent Teamsは以下のhookイベントで品質を強制できる:

- **`TeammateIdle`**: チームメイトがidle状態になるとき実行。exit code 2でフィードバックを送りて作業を継続させる
- **`TaskCompleted`**: タスクが完了マークされるとき実行。exit code 2で完了を阻止しフィードバックを送る

### チームメイトのモデル指定（v2.1.234 で `teammateDefaultModel` 廃止）

チームメイトのモデルは以下の**最初に該当したもの**が使われる:

1. spawn プロンプトがそのチームメイトに指定したモデル
2. サブエージェント定義から起動したチームメイトの場合、定義の `model`（`inherit` はリードのモデルを選ぶ）。**表示モードを問わず適用される**（従来は in-process のみ）
3. `CLAUDE_CODE_SUBAGENT_MODEL`（`inherit` 以外の値が設定されている場合）
4. リードの現在のモデル

> **v2.1.251 より前は `CLAUDE_CODE_SUBAGENT_MODEL` がこの順序の先頭**で、定義の `model:` と spawn 時の明示指定を上書きしていた。同変数は「すべてを上書きする」から「他で割り当てられなかった場合の**既定**モデル」へ意味が変わっている。ハーネス側で本変数に依存している場合、エージェント定義の `model:` が意図せず勝つようになった点に注意する（2026-09-01 巡回で公式 agent-teams ドキュメントが新順序に追随したことを確認）。

> **`CLAUDE_CODE_SUBAGENT_MODEL_FORCE=1`（v2.1.257）はチームメイトにも適用される。** 設定すると上記優先順位を無視して `CLAUDE_CODE_SUBAGENT_MODEL`（未設定ならリードのモデル）が全チームメイト・サブエージェント・ワークフローエージェントに強制される。v2.1.251 以前の「変数がすべてを上書きする」挙動に戻したい場合はこれを使う。設定が効いているかは、サブエージェント実行中に `/tasks` を開いて各行に表示されるモデル名で確認できる。詳細は公式 `sub-agents` の「Run every subagent on one model」節（2026-09-02 追加）を参照。

**`teammateDefaultModel` 設定キーは v2.1.234 で削除された。** 残存値は無視されるため、プロンプトでモデルを明示する。

組織の `availableModels` 許可リストとの突合と代替（**選ばれたモデル**に対して行われる）:
- **ファミリーエイリアス（`opus` 等）**: Anthropic API / Claude Platform on AWS では許可リスト内で最新版にフォールバック。プロバイダ固有モデルIDを使う環境（この置換が働かない）では次項の扱い
- **上記以外のブロック値**（置換が働かないプロバイダのエイリアス、許可版が存在しないファミリーを含む）: リードのモデルで実行。ただし `CLAUDE_CODE_SUBAGENT_MODEL` が設定されている場合は、同じ規則の下でまずそのモデルが試される

チームメイトはリードの effort level を継承する（split-pane モードでは v2.1.186 以降）。

## 7. チームメイト定義（.claude/agents/*.md）

`.claude/agents/` にMarkdownファイルとして定義し、spawn 時に名前で参照する。

**定義のどの部分がチームメイトに適用されるかは表示モードによって異なる**（ドキュメント改訂で明文化）:

| frontmatter | in-process | split-pane |
|:--|:--|:--|
| `tools` | 定義の許可リストに制限。`SendMessage` が追加され、[Task ツールを持つセッション](https://code.claude.com/docs/en/tools-reference#task-tool-availability)では `TaskCreate` / `TaskGet` / `TaskList` / `TaskUpdate` も追加 | 同左 |
| `model` | spawn プロンプトがモデルを指定していない場合に使われる（v2.1.251〜） | **同左**（v2.1.251 で split-pane でも使われるようになった。従来は無視） |
| 本文（body） | 既定のシステムプロンプトに**追記**される | 既定のシステムプロンプトを**置き換える** |
| `skills` | 適用されない（プロジェクト／ユーザー設定からロード） | 適用されない（同左） |
| `mcpServers` | 無視（プロジェクト／ユーザー設定からロード） | [サブエージェントの当該フィールドの規則](https://code.claude.com/docs/en/sub-agents#scope-mcp-servers-to-a-subagent)に従って適用される（`--agent` で開始したセッションと同じ扱い） |

定義で書く内容の目安:
- モデル選択（haiku, sonnet, opus）
- 利用可能ツール
- 実行フェーズ（初期化→作業ループ→シャットダウン）
- エラーハンドリング戦略

## 8. チームメイトへの直接操作

### in-processモード
- `Shift+Down`: チームメイト間を順に切り替え（最後のチームメイトの次はリードに戻る）
- `Enter`: チームメイトのセッションを表示
- `Escape`: 選択を解除。チームメイトのトランスクリプトを表示中は、そのチームメイトの現在のターンを中断
- `Ctrl+T`: タスクリストの表示/非表示切り替え
- テキスト入力で直接メッセージ送信
- in-process チームメイトのリクエストはメイン会話とは別のプロンプトキャッシュ TTL バケットに入るため、Claude サブスクリプションでも既定は 5 分保持。1 時間にするには `subagentPromptCacheTtl: "1h"`（API 側は 1 時間キャッシュ書き込みを高い単価で課金）

### split-paneモード
- 各チームメイトのペインをクリックして直接操作

## 9. コンテキストと権限

- チームメイトはリードの会話履歴を**引き継がない**。スポーン時のプロンプトのみ受け取る
- CLAUDE.md、MCPサーバー、Skillsは通常セッションと同様に読み込まれる
- 権限はリードの設定を引き継ぐ。スポーン後に個別変更可能だが、スポーン時に個別設定はできない

## 10. サブエージェント vs Agent Teams

| 観点 | サブエージェント | Agent Teams |
|------|----------------|-------------|
| 実行モデル | 単一セッション内。結果をcallerに返す | 独立インスタンス。完全自律 |
| 通信 | 結果の返却のみ | ピアツーピアメッセージング |
| 協調 | ハブ&スポーク（メインが管理） | 自己協調（共有タスクリスト） |
| コンテキスト | 結果が要約されて戻る | 各自独立コンテキスト。メッセージで共有 |
| 適用場面 | 集中並列タスク（調査、検証） | 協調が必要な作業（議論、交渉） |
| トークンコスト | 低い | 高い（3-4倍） |
| セットアップ | シンプル（Agent tool） | 実験的フラグ必要。オーバーヘッド大 |

### 判断フロー

```
調査・読み取りのみ？ → サブエージェント（Explore）
単一モジュール変更？ → サブエージェント（General-Purpose）
複数モジュール並列変更？ → Agent Teams
複雑要件（スコープクリープリスク）？ → Agent Teams + リマインダーエージェント
判断に迷う？ → サブエージェント（シンプルな方）
```

## 11. ベストプラクティス

### チームサイズ
- 最適: 3-5チームメイト
- 5-6を超えると協調オーバーヘッドが利点を上回る

### タスク設計
- チームメイトごと5-6タスク
- 自己完結型で明確な成果物
- **ファイル所有権を分離**（同一ファイルの同時編集は上書きによるデータロスの原因）

### リマインダーエージェントパターン
- Haikuモデルで低コスト運用
- 約60秒間隔でリードに要件・計画をリマインド
- スコープクリープ・品質低下を防止
- パッシブ受信（リードは読むが返信不要）

### 注意事項
- `/resume`でin-processチームメイトは復元不可
- タスクステータスが更新されないことがある（手動確認推奨）
- チームメイトのシャットダウンに時間がかかる場合がある
- ネストされたチームは不可（チームメイトがチームを作ることは不可）

## 12. 強力なユースケース

### 並列コードレビュー
```
3人のレビュアー: セキュリティ担当、パフォーマンス担当、テストカバレッジ担当
```

### 競合仮説デバッグ
```
5人の調査員が異なる仮説を並列検証。相互に議論して仮説を反証
```

### クロスレイヤー機能開発
```
API担当、DBマイグレーション担当、テスト担当が並列作業
```

## 13. 制限事項（公式）

- `/resume`、`/rewind`でin-processチームメイトは復元不可
- タスクステータスが更新されない場合がある（依存タスクがブロックされる）
- チームメイトのシャットダウンに時間がかかる（現在のリクエスト/ツール完了まで待機）
- 1セッション1チームのみ（前のチームをクリーンアップしてから新チーム作成）
- ネストされたチーム不可（チームメイトがチーム作成不可）
- リード固定（チームメイトをリードに昇格不可）
- 権限はスポーン時にリードから引き継ぎ（個別設定は後から変更可能だがスポーン時は不可）
- split-paneはVS Code統合ターミナル、Windows Terminal、Ghosttyでは非サポート

## 14. Codex CLIとの比較

Codex CLIにはAgent Teamsの直接的な対応機能は**存在しない**。
Codexの`multi_agent`フィーチャーフラグはあるが、Claude CodeのAgent Teamsとは異なる実装。

| 機能 | Claude Code | Codex CLI |
|------|------------|-----------|
| マルチエージェント協調 | Agent Teams（実験的） | multi_agent（フィーチャーフラグ、詳細不明） |
| ピアツーピアメッセージ | ✅ | ❌ |
| 共有タスクリスト | ✅ | ❌ |
| チームメイト定義 | .claude/agents/*.md | ❌ |

→ mapping分類: **claude-native**
